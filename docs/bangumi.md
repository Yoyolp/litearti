# 发现：Bangumi 资料的边界与取舍

> 状态：**已实现**，「发现」板块的推荐与新番时间表

---

## 一、为什么有这个功能

番剧源解决的是「我想看某部番，去哪里下载/在线看」。但另一半问题没人回答：**有什么值得看**。

Kazumi 用 Bangumi 的数据回答了它，这里照做。两个功能：

| 功能 | 回答的问题 | 数据来源 |
|---|---|---|
| 推荐 | 现在大家在追什么 | 热门列表 |
| 新番时间表 | 这周几更新、这一季有什么 | 季节日历 |

---

## 二、联网边界（这条改了既有承诺）

README 原来写着「源是唯一会联网的板块」。加了发现之后不成立，所以改了：

**现在有两处联网，都只走 Rust：**

| 通道 | 模块 | 只访问 | 发送什么 |
|---|---|---|---|
| 源 | `net.rs` | 你添加的源指向的网站 | 搜索词、页面请求 |
| 发现 | `bangumi.rs` | `api.kazumi.fyi` | 季度日期、分页参数 |

**发现通道不发送**：不发送任何本地数据、不发送设备信息、不发送账号（没有账号）。
`User-Agent` 是 `litearti/<版本>`，不是浏览器 UA —— 镜像运营者看到日志时应该能认出这是什么。

`net.rs` 的模块注释原来写着「唯一会联网的地方」，也一并改了。

## 三、为什么用镜像而不是直连

写这个功能时，`api.bgm.tv` 和 `next.bgm.tv` 的 **TCP 443 完全不通**（`Test-NetConnection` 返回 False），而 `api.github.com`、`baidu.com` 正常。这不是全局网络问题，是这两个域名在当时的网络下不可达。

Kazumi 有三种模式：直连、ECH（加密握手）、镜像。它的镜像是 `api.kazumi.fyi`，实测可用。

**所以这个项目从一开始就用镜像。** 这不是最优解，是最早能跑通的解，如实记下来。

### 镜像只代理两个端点

| 需要的 | 镜像有 |
|---|---|
| 季节日历 `/kazumi/v1/calendar/season` | ✅ |
| 热门列表 `/kazumi/v1/popular/subjects` | ✅ |
| 番剧详情 | ❌ |
| 关键词搜索 | ❌ |

**这直接决定了信息架构**：没有详情页可跳，所以每张卡片必须自带足够的信息（封面、标题、评分、播出日期就在列表响应里）。点击卡片不等于「打开详情」，而是**去你自己的源里搜这部番** —— 这是唯一能真正通向「看到」的动作。所以按钮叫「在源里找」。

## 四、两个端点的结构差异（实测，已做成 fixture）

`scripts/fixtures/bgm-calendar.json`（80 部）和 `bgm-popular.json`（24 部）是**真实响应**，原样提交。

| 字段 | 日历端点 | 热门端点 |
|---|---|---|
| 顶层形状 | `{ "1": [{subject}], ... "7": [...] }` | `{ data: [subject] }` |
| 需要剥一层 `subject` | **是** | **否** |
| `rating.count` | 对象 `{"1":6,...}` | **数组** `[7,4,...]` |
| `date` | 有 | **没有** |
| `metaTags` `platform` `series` `locked` `nsfw` | 没有 | 有 |
| `nameCN` / `name_cn` | 两个都有 | 两个都有 |

**解析器必须同时吃两套形状。** `src/discover/subject.ts` 里每个字段都可选、都宽容，`rating.count` 干脆不读（两份形状不同，而这个应用不用直方图）。

这一点由 `scripts/verify-bgm-parse.mjs`（29 项）用真实 fixture 守着。手写 fixture 只会验证「解析器能解析作者想象中的结构」。

## 五、匹配：为什么这里可以模糊

上一轮为**跨源重匹配**定的是「标题完全相等」。这里不一样，理由要写清楚：

| | 跨源重匹配 | 发现 → 源搜索 |
|---|---|---|
| 做什么 | **覆盖**已有条目指向的源 | 打开一个搜索结果 |
| 配错的代价 | 条目静默指向错误的番，可能看一整集才发现 | 列表里多一个错结果 |
| 配不上的代价 | 条目一直显示失效，看得见 | 什么都不发生，自己手动搜 |

重匹配会改写已存数据，所以门槛是「可证明是同一部」。这里最坏情况是排序错，而完全相等在 Bangumi 标准名和源站标题之间会漏掉大部分 —— Bangumi 写「孤独摇滚！」，源站写「孤独摇滚 第一季」。

### Dice 系数 + 去掉续作标记

用的是字符二元组 Dice 系数。但**原始 Dice 有个真 bug**，实测发现：

```
目标「进击的巨人」
  0.800  进击的巨人 中学      ← 恶搞番外，排第一
  0.727  进击的巨人 第一季    ← 正片，排第二
```

原因是 Dice 对**更短的后缀惩罚更小**，于是「中学」压过「第一季」。自动选中会把用户带进错误的作品。

**修法**：打分前剥掉「续作标记」——`第X季`、`第X期`、`最终季`、`Season N`、`第N部分`。剥掉后：

```
1.000  进击的巨人 第一季
1.000  进击的巨人 最终季
0.800  进击的巨人 中学
0.727  进击的巨人 剧场版
```

**只剥续作标记，不剥「剧场版/番外/OVA/中学」** —— 那些是不同的作品，剥了会让它们和正片打平。

### 已知无法区分的

`钢之炼金术师` 和 `钢之炼金术师 FA` 相似度 0.83，**没有任何阈值能分开它们**。这类情况靠平局规则：按源站搜索结果的原顺序取第一个（源站的排序本身就是相关性信号，比这里另发明一个更可信）。

## 六、限速与缓存

Bangumi 的公开要求是 1 秒 1 次。镜像也是别人的服务器，至少该给这个礼遇。

| 机制 | 实现 |
|---|---|
| 限速 | 全局一个 `Mutex<Option<Instant>>`，持锁等待，保证并发调用不会同时放行 |
| 缓存位置 | `app_data_dir()/sources/bangumi-cache.json` |
| 日历 TTL | 6 小时 |
| 热门 TTL | 1 小时 |
| 失败回退 | 网络失败时用**过期缓存**，而不是报错 |

失败回退这条是刻意的：早上拉到的日历比空白页有用得多。

## 七、封面图：设计系统的一个例外

`docs/design-system.md` 原来写着「从不加载外部封面」。发现页破了这条，理由：

- 那条规矩是为**本地书架**定的——本地文件没有封面，去外部找一个既慢又常错。
- 新番时间表**本身就只有封面和标题**，不显示封面等于放弃了它一半的用处。
- 例外范围**严格限定在发现页**。资料库仍然是文字排版的书脊。

### 7.1 封面缓存是必需的，不是优化

封面来自 `api.bgm.tv` / `lain.bgm.tv`，实测**两个域名在本机全部不可达**（`api.kazumi.fyi` 也不代理图片，返回 404）。

不缓存的话：一屏 24 张卡片，每次渲染各发一次请求，每个都挂到超时才放弃 —— 界面看着正常，实际上一分钟都在做无用功。

所以缓存做两件事：

| 方向 | 行为 |
|---|---|
| 成功 | 存到 `app_data_dir()/sources/bangumi-covers/<hash>.<ext>`，之后走 asset 协议本地读取 |
| **失败** | 记进 `bangumi-cover-failures.json`，**1 小时内不再重试** |

负缓存是实测出来的需求：加了它之后，同一张封面第二次调用从 **10024ms** 降到 **6ms**。

配套约束：

- 只接受 http/https —— 封面 URL 来自远程 API，不可信。`file:` 会让这个命令变成任意文件读取器。
- 上限 3 MB、超时 10 秒。
- 文件名用 FNV-1a 哈希：URL 里有文件系统不接受的字符，也可能超长。
- 失败记录文件**不计入**缓存统计（否则空缓存会显示「1 个文件」）。

## 八、规则镜像

社区规则放在 GitHub 上，`raw.githubusercontent.com` 在部分网络不通。实测（Rust 客户端）：

| 镜像 | 结果 | 条数 |
|---|---|---|
| **GitCode** | 368ms | **17** |
| gh-proxy | 1746ms | 18 |
| 直连 GitHub | 349ms | 18 |

**注意：GitCode 镜像滞后一条**（缺 `TvTFun`）。镜像更新是独立进行的，这是关于世界的事实，不是 bug —— 所以选择器给了三个选项让人自己切。默认仍是 GitCode（国内网络下最可能通、最快）。

设计上两条硬约束：

1. **镜像列表编在 Rust 里，前端只传 id**。如果允许传 URL，这个命令就成了通用代理，而 `net.rs` / `proto.rs` 小心翼翼守的正是这条线。
2. **规则名要在拼 URL 前校验**。名字来自远程索引，是远程输入；`../escape`、`a/b`、`name?x=1` 全部拒绝。

大小写敏感是有意的：`MXdm` 和 `mxdm` 是两个不同的请求，后者 404。**不做大小写回退** —— 那会把「镜像挂了」伪装成「规则解析失败」。

缓存：索引 1 小时，规则文件 24 小时。与 Bangumi 客户端不同，这里**失败不回退到过期缓存** —— 手动打开规则面板时，看到「这个镜像连不上」比看到一份可能很旧的列表更有用，而补救办法（换镜像）就在旁边。

## 九、收藏状态：本地，不是 Bangumi 账号

四个状态沿用 Bangumi 的词汇（想看 / 在看 / 看过 / 搁置），因为人已经知道它们是什么意思。但**纯本地**，存在 `localStorage` 的 `litearti.bangumi.collect`，不发给任何人。

**为什么不放在资料库里**：资料库放的是「你能打开的东西」。收藏状态是对一部**可能还没地方看**的番的备注（「等它播」）。绑到资料库条目上意味着必须先加入才能标记，反了 —— 时间表才是你**发现**要加什么的地方。

两者可以同时存在，回答不同的问题：「我在意这部吗」和「我能打开它吗」。

## 十、测试

| 脚本 | 覆盖 | 是否需要网络 |
|---|---|---|
| `verify-bgm-parse.mjs` | 解析器 vs **真实 fixture**，29 项 | 否 |
| `verify-bgm-match.mjs` | 相似度、排序、续作标记修正，含真实番剧名 | 否 |
| `verify-ui-discover.mjs` | 界面、收藏、筛选、换季、去源里搜，23 项 | **是** |
| `verify-mirror-cover.mjs` | 规则镜像、封面缓存与负缓存，25 项 | **是** |

`verify-ui-discover.mjs` 要网络的取舍：它测的是**应用自己的请求路径**，用 fixture 服务器替掉镜像就测不到那一半。解析本身已由离线脚本用真实抓取覆盖，所以它的职责只有「屏幕能不能加载、显示对不对、标记能不能用」。

换网络环境后如果它失败，先看是不是镜像不可达，而不是代码错了。

## 十一、还没解决的

- **镜像可用性不由我们控制。** 它是 Kazumi 项目的服务。如果它下线，发现板块就没了，而应用里没有回退方案（直连在这台机器上本来就不通）。
- **GitCode 镜像会滞后。** 实测比上游少一条规则。三个镜像的更新各自独立，没有自动比对机制。
- **没有详情页。** 简介只在卡片上有截断，看不到完整内容 —— 因为镜像不代理详情端点。
- **没有搜索。** 不能用关键词在 Bangumi 里找番，只能翻推荐或时间表。
- **`剧场版` / `番外` 无法与正片区分。** 它们分数低于正片但仍在阈值之上，会出现在候选列表里。
